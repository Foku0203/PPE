## 1. บทนำ

### 1.1 วัตถุประสงค์ของเอกสาร
เอกสารฉบับนี้ระบุความต้องการของระบบแอปพลิเคชันบริหารจัดการและเบิกจ่ายอุปกรณ์คุ้มครองความปลอดภัยส่วนบุคคล (PPE) เพื่อใช้เป็นฐานร่วมสำหรับการออกแบบ พัฒนา ทดสอบ จัดซื้อ และตรวจรับระบบ

### 1.2 วัตถุประสงค์โครงการ
1. พัฒนาระบบให้การเบิกจ่าย PPE สะดวก รวดเร็ว และถูกต้อง
2. เพิ่มประสิทธิภาพการบริหารคลัง ลดการขาดแคลน และป้องกันการเบิกจ่ายซ้ำซ้อน

### 1.3 ขอบเขตระบบ
ระบบครอบคลุมการยืนยันตัวตน ค้นหา PPE หลายภาษา ยื่นคำขอ อนุมัติ จ่ายของ ตัดสต็อกแบบ Real-time ติดตามอายุการใช้งาน/โควต้า แจ้งเตือน และรายงานสำหรับพนักงาน หัวหน้างาน และเจ้าหน้าที่คลัง/จป.

ไม่รวมการจัดซื้อจัดจ้างเต็มรูปแบบ บัญชีเงินเดือน และระบบควบคุมการเข้าถึงพื้นที่ เว้นแต่มีการตกลงเป็นโครงการต่อเนื่อง

## 2. ผู้มีส่วนได้ส่วนเสียและผู้ใช้งาน

| กลุ่ม | ความรับผิดชอบ/ความต้องการ |
|---|---|
| Worker | ขอเบิก ตรวจสอบสถานะ และดูประวัติของตนเอง |
| Supervisor | พิจารณาความจำเป็น อนุมัติคำขอ และติดตามภาพรวมทีม |
| Store Keeper / Admin | ตรวจสอบ อนุมัติ จ่ายของ จัดการคลัง และรายงาน |
| จป./EHS | กำหนดนโยบายโควต้า/อายุการใช้งาน อนุมัติกรณีพิเศษ และตรวจสอบ Audit |
| ผู้บริหาร | ดู KPI สต็อก การใช้ PPE และความเสี่ยง |

## 3. สมมติฐานและข้อจำกัด
- มี Employee ID ที่ไม่ซ้ำกัน และมีข้อมูลหน่วยงาน/หัวหน้างานจาก HR หรือ Directory
- อุปกรณ์ปลายทางรองรับกล้องและ QR Scanner ตามนโยบายองค์กร
- Push Notification ต้องอาศัยบริการเครือข่ายที่องค์กรอนุมัติ
- กติกาโควต้า อายุการใช้งาน และ Reorder Point ต้องกำหนดโดย EHS/คลังตามชนิด PPE
- ข้อมูลชีวมิติ/ใบหน้าต้องอยู่ภายใต้นโยบาย PDPA และกฎหมายที่เกี่ยวข้อง โดยระบบควรเก็บ Template/ผลยืนยันเท่าที่จำเป็น

## 4. ภาษาและประสบการณ์ใช้งาน
- รองรับภาษาไทย อังกฤษ และพม่า โดยเลือกภาษาได้จากโปรไฟล์/หน้าล็อกอิน
- ชื่อ PPE ปุ่มหลัก และข้อความผิดพลาดต้องมีคำแปลครบทั้ง 3 ภาษา
- ใช้ Visual Icons ประกอบรายการและขั้นตอน เพื่อช่วยแรงงานข้ามชาติและผู้มีข้อจำกัดด้านการอ่าน
- รองรับการแสดงผลบน Mobile และ Web Responsive; ภาษาไทย/พม่าต้องไม่ทำให้ปุ่มหรือข้อมูลล้นพื้นที่

## 6. ความต้องการเชิงหน้าที่

### FR-01 User & Authentication
1. เข้าสู่ระบบด้วย Employee ID และรหัสผ่าน/OTP ตามนโยบายองค์กร
2. รองรับ QR Code สำหรับระบุผู้ใช้หรือคำขอ โดยต้องตรวจสอบสิทธิ์ซ้ำก่อนทำรายการสำคัญ
3. รองรับ Face Scan เป็นทางเลือกเมื่ออุปกรณ์และนโยบายอนุญาต โดยต้องมีวิธีสำรอง
4. ล็อกบัญชี/แจ้งเตือนเมื่อพบความพยายามผิดปกติ และบันทึก Audit Log
5. ระบบต้องใช้ Role-Based Access Control และห้ามผู้ใช้ข้ามสิทธิ์ด้วยการแก้ URL/API

### FR-02 PPE Catalog & Requisition
1. แสดงรายการ PPE พร้อมชื่อไทย อังกฤษ พม่า ไอคอน รูปภาพ หน่วย ขนาด และคงเหลือ
2. ผู้ใช้เลือกชนิด จำนวน ขนาด/ความพอดี และเหตุผลการเบิก เช่น ใหม่ ชำรุด สูญหาย งานใหม่ หรือเปลี่ยนตามอายุ
3. แสดงโควต้า วันเบิกได้ครั้งถัดไป อายุการใช้งาน และคงเหลือก่อนยืนยัน
4. สร้างเลขที่คำขอแบบไม่ซ้ำ พร้อมวันเวลา ผู้ขอ หน่วยงาน และรายการ
5. Worker แก้ไข/ยกเลิกได้ก่อนอนุมัติ ตามเงื่อนไของค์กร

### FR-03 Anti-Duplicate, Quota & Lifespan
1. ตรวจสอบคำขอค้างอนุมัติ/อนุมัติแล้ว/รับแล้วของผู้ใช้ใน PPE เดียวกัน
2. ปฏิเสธหรือเตือนเมื่อเกินโควต้า หรือยังไม่พ้น Lifespan
3. หากต้องการเบิกก่อนกำหนด ให้เปลี่ยนเป็น `Special Approval` และบังคับกรอกเหตุผล/หลักฐานถ้ามี
4. กรณีพิเศษต้องได้รับอนุมัติจาก Supervisor และ จป./EHS ก่อนส่งให้คลังจ่าย
5. การตรวจสอบต้องเป็น Transaction เดียวกับการสร้างคำขอ เพื่อป้องกันการยื่นพร้อมกันซ้ำซ้อน

### FR-04 Inventory Management
1. รับเข้า โอน จ่าย คืน ชำรุด และปรับยอด พร้อมผู้ทำรายการและเหตุผล
2. ตัดสต็อกแบบ Real-time เมื่อจ่ายสำเร็จ และป้องกันยอดติดลบ
3. ตั้ง Reorder Point/Minimum Stock ราย PPE และแจ้งเตือนเมื่อคงเหลือต่ำกว่าเกณฑ์
4. บันทึก Batch/Lot และวันหมดอายุเมื่อเกี่ยวข้อง
5. Harness ต้องบันทึก Serial Number, Lot Number, วันผลิต, วันตรวจสภาพ, วันหมดอายุ และประวัติผู้รับ
6. รองรับ FIFO/FEFO ตามนโยบายคลัง

### FR-05 Approval & Notification
1. เส้นทางปกติ: Worker ส่งคำขอ -> Supervisor อนุมัติ -> คลังตรวจสอบ/อนุมัติ -> พร้อมรับของ -> รับสำเร็จ
2. ส่ง Push Notification แบบ Real-time เมื่อมีคำขอใหม่ ผลอนุมัติ สินค้าพร้อมรับ และรายการผิดพลาด
3. ผู้มีสิทธิ์ต้องเห็นเหตุผลและประวัติการอนุมัติ พร้อมวันเวลา
4. ห้ามข้ามขั้นอนุมัติ เว้นแต่มีสิทธิ์ Override ที่กำหนดและต้องบันทึกเหตุผล

### FR-06 สถานะการเบิกจ่าย
ใช้ 4 รหัสหลักที่ผู้ใช้งานเห็น:

| รหัส | ชื่อสถานะ | ความหมาย |
|---|---|---|
| PENDING_APPROVAL | รออนุมัติ | อยู่ระหว่าง Supervisor/จป./คลังพิจารณา |
| APPROVED | อนุมัติแล้ว | ผ่านเกณฑ์และรอการเตรียมของ |
| READY_FOR_PICKUP | พร้อมรับของ | คลังจัดของแล้ว ผู้ขอรับได้ |
| COMPLETED | รับสำเร็จ | ยืนยันส่งมอบและตัดสต็อกแล้ว |

สถานะภายในที่จำเป็น: REJECTED, CANCELLED, ON_HOLD_STOCK และ SPECIAL_APPROVAL_REQUIRED โดยต้องมีคำอธิบายที่ผู้ใช้เข้าใจได้

### FR-07 Dashboard & Reports
- Worker: คำขอค้าง สถานะ และประวัติ
- Supervisor: คำขอรออนุมัติ การใช้ PPE รายทีม และรายการผิดปกติ
- คลัง/EHS: คงเหลือ Reorder Alert คำขอค้าง การเบิกตามชนิด/หน่วยงาน และ Serial/Lot
- ผู้บริหาร: KPI การใช้จ่าย มูลค่าสต็อก อัตราขาดแคลน และ SLA
- ส่งออก CSV/PDF ตามสิทธิ์ พร้อม Mask ข้อมูลอ่อนไหว

## 7. ความต้องการไม่ใช่เชิงหน้าที่

| รหัส | ข้อกำหนด |
|---|---|
| NFR-01 Availability | เป้าหมายระบบพร้อมใช้งานไม่น้อยกว่า 99.5% ต่อเดือน ไม่รวมช่วงบำรุงรักษา |
| NFR-02 Performance | หน้าหลักตอบสนองภายใน 3 วินาทีที่ P95 ในเครือข่ายองค์กร; รายการสำคัญต้องป้องกันการส่งซ้ำ |
| NFR-03 Security | TLS, เข้ารหัสข้อมูลสำคัญขณะเก็บ/ส่ง, RBAC, MFA ตามความเสี่ยง, Session Timeout และ OWASP controls |
| NFR-04 Privacy | ขอความยินยอม/แจ้งวัตถุประสงค์สำหรับ Face Scan, จำกัดการเข้าถึง, Retention และสิทธิ์เจ้าของข้อมูล |
| NFR-05 Auditability | บันทึกผู้ทำรายการ เวลา ก่อน/หลังเปลี่ยนแปลง และเหตุผล แก้ไขย้อนหลังไม่ได้โดยผู้ใช้ทั่วไป |
| NFR-06 Scalability | รองรับผู้ใช้ [ระบุจำนวน] และรายการพร้อมกัน [ระบุจำนวน] โดยขยายทรัพยากรได้ |
| NFR-07 Accessibility | รองรับคีย์บอร์ด คอนทราสต์ที่เหมาะสม ไอคอนร่วมกับข้อความ และภาษาไทย/พม่า |
| NFR-08 Recovery | กำหนด RPO [ระบุ] และ RTO [ระบุ] พร้อมทดสอบ Backup/Restore |

## 9. Workflow และกติกาธุรกิจ
ดูรายละเอียดและ Mermaid Diagram ใน [03-workflow.md](03-workflow.md)

- ต้องตรวจสอบสิทธิ์และข้อมูลผู้ใช้ทุกครั้งที่เปลี่ยนสถานะ
- คำขอหนึ่งรายการอาจมีหลาย PPE แต่แต่ละรายการต้องผ่านกติกาโควต้าแยกกัน
- เมื่อสต็อกไม่พอ ให้พักคำขอเป็น `ON_HOLD_STOCK` และแจ้งคลัง/ผู้ขอ ห้ามตัดยอดติดลบ
- การจ่าย Harness ต้องสแกน/ยืนยัน Serial และสถานะการตรวจสภาพก่อนปิดรายการ
- การยืนยันรับของต้องกระทำโดยผู้ขอหรือผู้รับมอบอำนาจที่บันทึกไว้

## 10. Acceptance Criteria
- ผู้ใช้ทั้ง 3 ภาษาเข้าสู่ระบบและยื่นคำขอได้ โดยข้อความและไอคอนแสดงถูกต้อง
- ระบบป้องกันการเบิกซ้ำ/เกินโควต้า และบังคับ Special Approval ก่อนกำหนด
- คำขอเดินทางครบ 4 สถานะหลัก พร้อม Push Notification และ Audit Log
- การจ่ายสำเร็จตัดสต็อก Real-time และแจ้ง Reorder เมื่อถึงเกณฑ์
- Harness ทุกชิ้นที่จ่ายมี Serial/Lot และตรวจสอบย้อนกลับได้
- ผู้ใช้แต่ละบทบาทเห็น/ทำได้เฉพาะสิทธิ์ใน Matrix และการทดสอบ Security ผ่าน
- รายงานที่อนุมัติสามารถตรวจสอบย้อนกลับถึงคำขอและผู้ทำรายการ

## 11. ประเด็นต้องยืนยันก่อนออกแบบรายละเอียด
- จำนวนผู้ใช้ สาขา คลัง และช่วงเวลาการใช้งานสูงสุด
- สูตรโควต้า/Lifespan ของ PPE แต่ละชนิด และผู้อนุมัติกรณีพิเศษ
- HR/SSO, Push Service, QR/Face SDK และระบบจัดซื้อที่จะเชื่อมต่อ
- RPO/RTO, Retention, PDPA และนโยบายการเก็บภาพ/Template ใบหน้า
